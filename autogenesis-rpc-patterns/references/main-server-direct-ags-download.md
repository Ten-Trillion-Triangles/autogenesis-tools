# Main-server direct AGS download (the read-path bypass of server-extend)

The `binary-record-proxy-pattern.md` reference covers the server-extend metadata-only proxy (Option A: client → server-extend → AGS for metadata, client → AGS S3 for bytes). When the **main server itself** needs to read a player-uploaded binary record, the architecture is different — the main server has its own `AccelByteSdkProvider` and reads AGS directly, bypassing server-extend. This is the canonical pattern for the simulation-mode "rehydrate the player-selected map on session start" flow.

## Why the main server doesn't route through server-extend

The main server (`server`, JVM, port 9080, WebSocket) is the always-on gameplay server. It already has an `AccelByteSdkProvider` because billing, CloudSave, and the resume-game snapshot pipeline all hit AGS directly. Routing a read through server-extend would:

- Add a network hop between two local JVMs (9080 → 7070 → AGS).
- Force the main server to wait for server-extend's REST+SSE plumbing to be healthy, when the read should work even if server-extend is starting up or restarting.
- Lock the read to whatever subset of methods server-extend chose to expose.

The chosen path: main server gets its own `AccelByteSdkProvider` and downloads bytes directly. **Uploads still go through server-extend** (for validation + audit + the player-scope IAM path), but downloads read the same AGS records directly.

## The download pattern (canonical implementation)

**File**: `server/src/main/kotlin/maps/PlayerMapDownloader.kt`. Single `object` with one `fun downloadBytes(userId: String, mapId: String): ByteArray`. The flow:

```kotlin
fun downloadBytes(userId: String, mapId: String): ByteArray
{
    val sdk = AccelByteSdkProvider.sdk
    val namespace = AccelByteSdkProvider.namespace
    val binaryKey = "map-$mapId"   // or "player-<userId>-map-<mapId>" — match the upload key

    // Step 1: ask AGS for metadata + presigned download URL.
    val op = AdminGetPlayerBinaryRecordV1.builder()
        .namespace(namespace).userId(userId).key(binaryKey).build()
    val response = wrapper.adminGetPlayerBinaryRecordV1(op)

    val downloadUrl = response.binaryInfo?.url
        ?: throw RuntimeException(
            "PlayerMapDownloader: AGS returned no binaryInfo.url for $namespace/$userId/$binaryKey " +
            "(record metadata missing — was the upload completed?)"
        )

    // Step 2: HTTP GET the bytes from the presigned URL.
    return fetchBytes(downloadUrl, userId, binaryKey)
}
```

Three failure modes, each with a diagnostic that names the exact key being looked up:

| Failure | Exception |
|---|---|
| AGS rejects the metadata call (network, IAM, missing record) | `RuntimeException` from SDK wrapper |
| `binaryInfo.url` is null (record not yet committed, or `adminPutGameBinaryRecordV1` was skipped) | `RuntimeException("... AGS returned no binaryInfo.url for ... (record metadata missing — was the upload completed?)")` |
| HTTP non-2xx on the presigned GET | `RuntimeException("... presigned GET for ... returned HTTP <code>")` |

The diagnostic-must-name-the-key rule is load-bearing: when the operator greps the logs, the message tells them exactly which AGS record path failed without making them reverse-engineer it from a stack trace.

## The RPC wrapper (read-mode, not request/response on this surface)

**File**: `server/src/main/kotlin/maps/PlayerMapRpcHandlers.kt`. The wrapper is one line of business logic over the downloader:

```kotlin
@RpcMethod("server.loadPlayerMap", RpcDirection.SERVER)
suspend fun loadPlayerMap(context: RpcCallContext, request: LoadPlayerMapRequest): LoadPlayerMapResponse
{
    Logger.info(LogCategory.NETWORK, "PlayerMapRpcHandlers.loadPlayerMap: userId=${request.userId} mapId=${request.mapId}")
    val bytes = PlayerMapDownloader.downloadBytes(request.userId, request.mapId)
    return LoadPlayerMapResponse(bytes)
}
```

DTOs are in the same file:

```kotlin
@Serializable
data class LoadPlayerMapRequest(val userId: String, val mapId: String)

@Serializable
data class LoadPlayerMapResponse(val mapPackBytes: ByteArray)
```

The `ByteArray` round-trip works here because the payload is a KSP-generated response (the serializer is generated by the `@RpcMethod` machinery, not a hand-rolled `ByteArraySerializer`). The `map-<mapId>` key format on the upload side MUST match the `binaryKey` on the download side exactly — when the same player uploads via `server.extend.savePlayerMap` (server-extend) and the simulation game-init later downloads via `server.loadPlayerMap` (main server), both modules must agree on the key prefix.

## Reading the "is this live?" signal — the four-link KSP chain

When the user asks "can the server actually use this?", the answer is not "the file exists" — it's "the KSP-generated provider is referenced from the master initializer, the runtime reflection call loads it, the provider registers the handler, and the compiled class is on the classpath." The full chain is:

1. **Source file** declares `@RpcMethod(name, RpcDirection.SERVER) suspend fun handler(...)` on an `object` or class.
2. **KSP processor** (`rpc-ksp/src/main/kotlin/org/ttt/autogenesis/ksp/RpcProcessor.kt:104`) generates `Generated<Name>RpcBindings.kt` with `register<Name>RpcHandlers(rpcRegistry, target)` + `<Name>RpcHandlersProvider` class + top-level `_$nameRpcHandlersProvider` val that calls `RpcRegistrationCollector.registerProvider(it)`.
3. **Master registration** (`server/build/generated/ksp/main/kotlin/org/ttt/autogenesis/network/generated/GeneratedRpcMasterRegistration.kt`) lists every provider via `_<name>RpcHandlersProvider` references inside an `internal val _rpcRegistrationInitializer = run { ... }` block.
4. **Runtime load** (`sharedModel/src/jvmMain/kotlin/org/ttt/autogenesis/network/RpcRegistrationPlatform.kt:6-15`) calls `Class.forName("org.ttt.autogenesis.network.generated.GeneratedRpcMasterRegistrationKt")` inside `initializeRpcRegistrationsPlatform()`, which is invoked from `registerRpcSystem()` at `Server.kt:51` (top-level `run { registerRpcSystem(); RpcRegistry(RpcDirection.SERVER) }`).

The `Class.forName` triggers the JVM class-init for `GeneratedRpcMasterRegistrationKt`, which evaluates the `run { ... }` block, which references every `_$nameRpcHandlersProvider` top-level val, which fires `RpcRegistrationCollector.registerProvider(it)` for each, which causes every subsequent `RpcRegistry.<init>` to call `<Provider>.register(this)` and bind the handler.

**Verification protocol** for "is this RPC actually live on the server side":

```bash
# 1. Source exists
ls server/src/main/kotlin/maps/PlayerMapRpcHandlers.kt

# 2. KSP generated the binding
ls server/build/generated/ksp/main/kotlin/org/ttt/autogenesis/network/GeneratedPlayerMapRpcBindings.kt

# 3. Master registration references the provider
grep "_playerMapRpcHandlersProvider" server/build/generated/ksp/main/kotlin/org/ttt/autogenesis/network/generated/GeneratedRpcMasterRegistration.kt

# 4. Compiled class is on the classpath
ls server/build/classes/kotlin/main/maps/PlayerMapDownloader.class
ls server/build/classes/kotlin/main/org/ttt/autogenesis/network/PlayerMapRpcHandlers.class
ls server/build/classes/kotlin/main/org/ttt/autogenesis/network/PlayerMapRpcHandlersRegistrationProvider.class

# 5. Test exists and ran (not just compiled)
ls server/build/test-results/test/TEST-maps.PlayerMapDownloaderTest.xml
```

If all five return, the handler is live and reachable from any module that can open a WebSocket to the main server. If any of them is missing, that's the gap to fix — not the handler body.

## The skill-search anti-pattern (corrected 2026-08-11)

When verifying whether a "download" function exists, the trap is to grep for `downloadMap` / `DownloadMap` / `fetchMap` / `loadMap` and miss the actual symbol. The `PlayerMapDownloader` is named that way but the **RPC** is `server.loadPlayerMap` — `loadPlayerMap`, not `downloadMap`. The grep that finds it is:

```bash
grep -rn "loadPlayerMap\|PlayerMapDownloader" server/src/main --include="*.kt"
```

**The lesson**: when the user asks "do we have a function to download X?", the search vocabulary must include both the verb the user used (download, fetch, get) AND the codebase's preferred verb (load, retrieve, read). Read the source-tree for the noun first (here: `PlayerMap` → `MapUpload*` files), then grep with the codebase's vocabulary. A blind search-by-user-terminology misses the code 100% of the time on this codebase.

## The "RPC handler vs callable function" decision (in-process callers)

When the main server's own `GameInit` needs to call `loadPlayerMap` from in-process (not over WebSocket), the cleanest path is to call `PlayerMapDownloader.downloadBytes(userId, mapId)` directly — same module, no network round-trip. The RPC wrapper stays for external callers (e.g. server-extend invoking download from its own bridge). Two-tier access is the canonical pattern:

- **In-process callers** in the same module: call the `object` directly.
- **Cross-module callers** (other JVMs, the browser): call the `@RpcMethod` handler via the WebSocket/gRPC bridge.

If the bridge is not hot when the in-process caller needs to load, the direct call still works (no network dependency). If the in-process caller uses the RPC instead, the request round-trips through the bridge — same code, wasted work.

## Other places this pattern applies

The same "main server has its own `AccelByteSdkProvider`, downloads directly from AGS" shape shows up in:

- **Resume-game snapshot rehydrate** — `GameRestoreRpcHandlers.restoreRunningGameForUser` reads `running-game` records via `AccelByteSdkProvider` (not via server-extend), even though the snapshot was originally written via server-extend's VFS proxy.
- **Billing / usage ledger** — `accounting/Billing.kt` calls server-extend's gRPC (Option: server → server-extend → AGS), but the underlying tool-shape is the same: a server-side SDK wrapper plus an HTTP fetch against a presigned URL.
- **GameRecord / AdminUserRecord** — `server/src/main/kotlin/accelbyte/cloudsave/GameRecord.kt:147, 206, 260` and `AdminUserRecord.kt:54, 212` all do `HttpClient.newHttpClient().send(...)` against AGS-issued presigned URLs, exactly the same shape as `PlayerMapDownloader.fetchBytes`.

The pattern is universal: server-side `AccelByteSdkProvider` + `HttpClient` + presigned URL. The "three-step" shape (admin/metadata → presigned URL → HTTP GET) is AGS's contract for binary records, and every binary read in the codebase follows it.
