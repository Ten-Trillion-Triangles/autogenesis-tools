# JSON Schema Ordering as Determinism Lever

The TPipe reasoning data classes aren't just response shapes. They are **control mechanisms** that exploit the LLM's left-to-right token prediction to force commitments before hallucination-prone fields are emitted.

## The Principle

Kotlin serializes `@Serializable` data class fields in **declaration order**. The LLM sees the JSON schema in that same order. Token prediction is left-to-right. Therefore:

> **The first field in the data class is the first commitment the LLM makes. The last field is the most flexible.**

This is structurally identical to writing imperative code with state dependencies: declare the state you want fixed first, then derive the rest from it. The LLM does exactly this. Every time.

## The Canonical Example: `doesLegendExist`

**File:** `TPipe/src/main/kotlin/Structs/ModelReasoning.kt:454-467`

```kotlin
/**
 * The reasoning pipe's analysis of the legend mappings present in the compressed prompt.
 *
 * @param doesLegendExist Top labeled boolean used to force the llm to predict against weather there is or
 * is not a legend present at all. This is required because without this smaller models tend to just hallucinate
 * values to fulfil the desire to have non-empty values in the json output. But by forcing it to acknowledge that
 * no legend exists when it's empty, it should prevent the hallucinated values from appearing.
 */
@kotlinx.serialization.Serializable
data class LegendAnalysis(
    var doesLegendExist: Boolean = false,        // ← FIRST
    var codesFound: List<String> = listOf(),    // ← constrained by the boolean
    var mappings: List<String> = listOf()       // ← most flexible, comes last
)
```

The KDoc literally explains the technique. The boolean is the **commitment point**. Once the model predicts `false` (or `true`), the downstream lists must be consistent with that commitment. Without the boolean, smaller models would emit plausible-looking codes and mappings to fill the empty JSON — the classic "desire to have non-empty values" hallucination.

### The Demo

Given an empty compressed prompt (no legend present):

- **Without `doesLegendExist`:** model emits `codesFound: ["AB", "AC", "BA"]`, `mappings: ["AB: foo", "AC: bar", "BA: baz"]` — confident-sounding but fabricated.
- **With `doesLegendExist` first:** model emits `doesLegendExist: false`, then leaves `codesFound: []` and `mappings: []` — correct, because the boolean commitment constrains what follows.

One boolean. One structural position. One class of bugs eliminated.

Every reasoning method uses the same trick. The fields are ordered to make the LLM commit to a position before the hallucination-prone output:

Every one of these has its highest-leverage commitment at the top of the data class.

## The Schema Injection Mechanism

**File:** `TPipe/src/main/kotlin/Pipe/Pipe.kt:1942-1955`

The JSON schema is auto-generated by `JsonSchemaGenerator` (`TPipe/src/main/kotlin/Util/Schema.kt`) from the `@Serializable` data class, then injected into the system prompt as the LLM's output contract:

```kotlin
val defaultJsonOutput = """
    You must return your output only in Json format. ...
    All variables in the json output must have valid values that match their declared types.
    Never use null as a value - instead provide appropriate default values: empty strings for text fields,
    empty arrays for lists, empty objects for nested structures, 0 for numbers, and false for booleans.

    The json output schema is as follows: ${jsonOutput}
    ...
""".trimMargin()
```

The `false for booleans` and `0 for numbers` defaults in the instruction text are critical — they tell the LLM the **default commitment** to use when uncertain. The LLM now has two reinforcement layers: the structural order of the schema, and the textual instruction about defaults.

## The Footer Prompt (Completion Enforcement)

**File:** `TPipe-Defaults/src/main/kotlin/Defaults/reasoning/ReasoningBuilder.kt:317-321`

```kotlin
targetPipe.setFooterPrompt("""
    IMPORTANT: You must fill all json values of your output. This INCLUDES NESTED JSON OBJECTS!! Fully
    complete your json output when producing your response.
""".trimIndent())
```

A third reinforcement layer — appended as the last thing the LLM sees, telling it to fill every field. Combined with the schema and the defaults instruction, this is a three-layer commitment system:

1. **Structural order** of fields in the data class
2. **Default-value instructions** in the schema prompt
3. **Completion enforcement** in the footer prompt

## The Unravel Pattern

Each response class has an `unravel()` method that flattens the JSON back into a thought stream the parent pipe consumes as natural-language reasoning. This is the reverse path — the LLM emits structured JSON, TPipe serializes it back into readable prose for the parent pipe's context.

Example from `MultiPhasePlan.unravel()` (ModelReasoning.kt:291-321):

```kotlin
fun unravel(): String = buildString {
    append("Here's what needs solving: ${analysis.whatNeedsSolving}. ")
    append("I'm working within these limitations: ${analysis.limitations.joinToString(", ")}. ")
    // ...
    append("My plan consists of ${phases.size} phases over $totalDuration: ")
    // ...
}
```

The structure stays intact: the parent pipe sees the same commitment order the model produced. The `unravel()` order should mirror the JSON field order — if you reorder fields, rerun the `unravel()` output and confirm the parent pipe's context reads naturally.

## The Article Thesis

For the "Reasoning Pipes Explained" blog post (Post 6, in flight):

> **TPipe doesn't prompt. It programs.** Left-to-right token prediction is a compiler for sequential commitment. By designing JSON schemas where the FIRST fields are boolean/int commitments and the LATER fields are the hallucination-prone content, TPipe forces the LLM to lock in a position before it ever touches the rich output. The `doesLegendExist` field is the cleanest example: a single boolean, structurally positioned first, kills an entire class of hallucinations in smaller models. The same trick scales across every reasoning method. Once you see it, you can't unsee it — and you can't build a serious LLM application any other way.

## How to Design a New Response Class Using This Pattern

1. **Start with the commitment fields.** Booleans, enums, and small string constraints go first. These are the LLM's "decisions."
2. **Then the structured analysis.** Lists, nested objects with limited cardinality. The LLM "reasons" through these.
3. **Then the rich output.** The actual answer, the deep prose, the final synthesis. The LLM "commits" to this.
4. **Order matters more than names.** The KDoc on `doesLegendExist` is explicit: "Top labeled boolean used to force the llm to predict against." Position is the mechanism.
5. **Match field order to the `unravel()` output order.** The thought stream the parent pipe sees should match the JSON prediction order the model used.
6. **Use the default-value instructions and the footer prompt** as reinforcement layers, not replacements for structural order.

## Anti-Patterns

- **Putting lists or strings first, booleans second.** The LLM commits to a hallucinated list, then justifies it with a forced boolean. The boolean comes too late to do any work.
- **Reordering fields without rerunning the `unravel()` tests.** The order in JSON does not have to match the order in `unravel()`, but the LLM's predictions follow JSON order, and the parent pipe's context follows `unravel()` order. Keep them in sync or reasoning chains break.
- **Adding a boolean to the END of an existing class.** Late-stage booleans are reactive ("did I do this right?"), not proactive ("I commit to this position first"). Reactive booleans don't railroad anything — the rich output has already been emitted.
- **Replacing structural ordering with longer instructions.** Instructions can be ignored. Field position cannot. If a hallucination is happening, move a boolean up, don't add a sentence to the system prompt.
- **Treating the JSON schema as documentation.** The schema IS the prompt. The structural order of fields is the mechanism that controls the LLM's behavior. The injected schema and the footer prompt are reinforcements, not the primary lever.
